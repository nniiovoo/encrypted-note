# Quick Unlock on Mac: local Secure Enclave custody

Status: ready-for-human — implementation present in this source tree; physical acceptance pending. Refs [#12](https://github.com/nniiovoo/encrypted-note/issues/12). Windows Hello remains later.

## Selected architecture

Quick Unlock uses a small native Swift CryptoKit adapter and an encrypted file managed by Rust. It needs supported Secure Enclave/Touch ID hardware and an enrolled finger. The app route requires no account, server, Apple Developer membership, provisioning profile or persistent Keychain item. It never sends a secret over the network. Local build and actual biometric acceptance are separate checks; the hardware behavior below still needs a recorded physical test.

The protected payload contains only the Vault Key and its binding to this computer's committed Vault. It never contains the Master Password, Recovery Key, Wallet Key or decrypted Notes. A real Secure Enclave private-key operation must release the wrapping secret; a successful fingerprint check represented as a boolean cannot open a Vault. There is no new Vault credential slot or Vault file-format change.

Source boundaries:

- [vault-format custody](../crates/vault-format/src/quick_unlock.rs) builds and parses an exact 80-byte wiping payload. Its non-secret SHA-256 binding covers Vault identity, KDF parameters and both complete credential slots, excluding the changing body nonce. Enrollment first authenticates the committed file with the held Vault Key. Reopening checks the binding, file structure/KDF limits and authenticated current body before returning an open Vault.
- [The Swift adapter](../src-tauri/native/biometry.swift) creates a Secure Enclave P-256 key-agreement key with WhenPasscodeSetThisDeviceOnly and the privateKeyUsage plus biometryCurrentSet constraints. It uses no userPresence, biometryAny, device-passcode fallback or OR policy. Apple documents the [Secure Enclave key-agreement interface](https://developer.apple.com/documentation/cryptokit/secureenclave/p256/keyagreement/privatekey) and [current biometric-set invalidation](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/biometrycurrentset).
- A fresh software P-256 ephemeral key agrees with the enclave public key during enrollment. HKDF-SHA256 derives an AES-256-GCM wrapping key using a random salt and a domain plus the complete envelope header. The header, including the encrypted enclave representation, both public keys, binding and nonce, is also AES-GCM associated data. The ephemeral private key is never saved. On read, the enclave private ECDH operation is required to reconstruct the secret and authenticate the payload. Apple's [CryptoKit storage example](https://developer.apple.com/documentation/cryptokit/storing-cryptokit-keys-in-the-keychain) explains that an enclave key's representation is an encrypted block usable by the same enclave, rather than its raw private key; this implementation stores that representation in its own file.
- [The Rust file adapter](../src-tauri/src/biometry.rs) bounds the envelope at 32 KiB. It requires a private parent directory, an owner-owned regular file with mode 0600 and one link, and rejects symlink components, hard links and special files. It writes a new exclusive temporary file, syncs it, publishes without overwriting an existing registration, and syncs the directory. The encrypted file is separate from the Vault's credential slots and normal Backup contents.

## Lifecycle and failure rules

| Event | Implemented rule |
|---|---|
| Enable, initially off | Freeze the current action and obtain a fresh native Master Password check of the committed Vault. Persist disabled policy before replacing a stale registration. Write the encrypted file, then perform a fresh biometric-gated read-back and authenticate the returned key against the committed Vault before persisting enabled status. Failure or cancellation leaves Quick Unlock off and the Vault unchanged. |
| App start, crash or relaunch | Require native Master Password verification before any Quick Unlock, even when an encrypted registration survives. The saved binding never authorizes the process by itself. |
| Seven-day deadline | Rust records a process-local deadline from the last successful native Master Password verification of the current Vault. The continuous clock counts sleep. Expiry, a missing clock, backward time or overflow revokes authorization. Core ticks observe expiry while Locked too. Touch ID never extends the deadline. |
| Ordinary lock, sleep, screen lock or user switch | Keep the encrypted registration, drop the open Vault/decrypted Notes, and invalidate pending native authentication. A later unlock needs another protected private-key operation within the process deadline. |
| Biometric request | Use a fresh LAContext with reuse disabled, paired with Apple's embedded `LAAuthenticationView` in a native panel inside the protected main window ([#95](https://github.com/nniiovoo/encrypted-note/issues/95)). The system alert would take focus and be cancelled by the app-switch rule, which stays as it is: no focus exemption or process allowlist. Request biometrics only in that view, then perform the real Secure Enclave operation with the same context and further UI refused; the view's success never authorizes anything by itself. A read with no presented view does not start. Closing the panel (Cancel, Escape, focus loss, Lock, the Sharing Guard, expiry) cancels the request and invalidates its context. Run protected work outside the core mutex, then recheck generation, phase, operation deadline and the exact current file before committing the ordinary session. Late callbacks are discarded. |
| Cancel, failed match, lockout, unavailable hardware or malformed file | Stay Locked, drop returned wiping buffers, give a sanitized fallback message and offer native Master Password entry. Never fall back to the Mac login password or clear password-attempt backoff. Invalidated or mismatching registrations require explicit re-enrollment. |
| Changed enrolled fingers | The current-set constraint makes the protected key unavailable. Require native Master Password verification and explicit enrollment; do not recreate a weaker key automatically. |
| Master Password change, recovery reset, Backup/Safety Copy installation | Disable registration and process authorization before the transition, including an installation with the same Vault ID or identical header. Inspecting a copy does not authorize Quick Unlock. |
| Key Rotation | Disable registration as soon as rotation starts. Cancellation/failure does not enroll pending keys. After the new Recovery Kit is confirmed and the Vault saved, explicit enrollment is required again. |
| Disable or stale registration | Mark the process unavailable, persist disabled policy, then remove only the exact private registration file. Failed persistence prevents scheduled old-registration cleanup and the credential transition; failed cleanup keeps app policy off and shows a warning. A newly written, uncommitted enrollment is cleaned up on failure. |

The [pure gate](../src-tauri/src/quick_unlock.rs), [core coordinator](../src-tauri/src/core/quick_unlock.rs) and native operation checks own these rules. A Recovery Key, a credential used only to inspect a copy, or a biometric operation cannot refresh the seven-day deadline. Normal save body nonces may change without invalidating registration. Credential-slot changes cannot.

Quick Unlock starts the existing idle, Sharing Guard, clipboard and Trash behavior. It preserves the password-attempt count and delay. The WebView receives availability and outcomes only. Wallet Kind actions still require a fresh native Master Password check and a transient Wallet Key under ADR-0004; the biometric payload cannot release a Wallet Key. See [native credential custody](native-credential-design.md).

## Boundaries and acceptance still pending

This file uses filesystem access controls, not Keychain application access-group isolation. A process with the same user's file access may copy the encrypted representation and request its own Secure Enclave operation. The startup and seven-day Master Password gates are policy enforced by this app, not a cross-process restriction on such a copied blob. An unexpected biometric prompt must not be treated as permission for the app's intended action.

Disabling removes the current registration file. It does not promise secure erasure from APFS snapshots, system backups, other copies or storage remnants, and does not cryptographically revoke an older copied representation on the same device. The app refuses stale bindings, while an old Vault copy remains protected according to its own older credentials and any surviving device-bound copy. Treat the registration file as sensitive local backup material.

Rust wipes its payload/key buffers. Swift resets the plaintext Data it owns where the API permits; CryptoKit, LocalAuthentication, AppKit, OS copies and the stack remain best effort. Quick Unlock does not protect a compromised native process, administrator or operating system and never grants an agent access to the owner Vault.

Fake-data tests cover custody, ordinary-save versus slot binding, startup, seven-day boundaries, missing/backward clocks, stale callbacks, cancellation, wrong items, credential/rotation/copy transitions, persistence failures and cleanup ordering. Private-file tests cover publication, permissions, bounds and malformed input without creating an enclave key. These tests and compilation do not establish physical biometric behavior.

Physical acceptance remains open on an actual supported Mac running the local build: enable/read-back, cancel/retry, failed match and lockout, no login-password fallback, finger enrollment changes, app/OS restart, sleep/screen-lock/user-switch/app-switch races, deadline expiry, password/recovery/Backup/rotation transitions, disable/cleanup failure, file-copy restoration and app update. Record sanitized app/OS/hardware versions and outcomes. Do not record real secrets, recovery text or private file contents. Windows native credential behavior and Capture Hiding have their separate physical test matrix; Windows Hello is not implemented.
