# An optional Agent Companion helper, in its own sandbox, may run the approved OpenAI operation

Status: Accepted by the owner, 2026-10-26 (integration design and scoped exceptions approved). Implemented with fictional data only; real credential provisioning, OS account changes, live provider calls and the ChatGPT connection remain owner actions.

The owner wants one place to manage the restricted OpenAI companion ([ADR-0008](0008-agent-gateway-awaits-a-concrete-api.md)) from inside encrypted-note, without giving it any part of the **Vault**. This records the one exception to "the app offers no agent interface" ([ADR-0007](0007-agents-use-separate-restricted-keys.md)), "no network code" ([ADR-0001](0001-local-only-vault-moved-by-hand.md)) and "every key in the Rust core" ([ADR-0003](0003-tauri-with-secrets-kept-in-rust.md)). Everything outside the exception stays as those decisions say.

## Decision

- **A separate helper, not a separate thread.** encrypted-note.app may contain the **Agent Companion** helper: an XPC service (`<app identifier>.companion`) with its own App Sandbox and its own container. A fictional-data spike (2026-10-26, macOS 26.4.1) showed why a plain child process isn't enough: a child of the sandboxed app inherited the app's sandbox and could read a fake Vault canary in the app's container, whereas the XPC service could neither read nor list it. Only the containing app can connect to the helper, which also checks the app's code-signing identifier.
- **What the helper may do.** It may hold one separately created OpenAI **Agent Key**, make only the fixed `generate_text` request (POST `https://api.openai.com/v1/responses`, model `gpt-6-luna`, the companion's input/output/rate limits) and listen on loopback `127.0.0.1:8789` for the separate agent account's bridge. Its entitlements (`network.client`, `network.server`, one read-write exception for `/Users/Shared/encrypted-note-companion/`) are the helper's only; the Vault app's entitlements are unchanged.
- **What never reaches the helper.** No Vault file, Note, Note metadata, Note API key, Wallet Kind, Seed Phrase, Private Key, **Master Password**, **Recovery Key**, **Backup**, **Safety Copy** or path to them. The helper's protocol carries four numbers back to the app (state, readiness flags, grant expiry, error code) and accepts four operations (status, start, stop, install). Owner setup passes two already-open files that the owner picked in OS panels; the app never reads them.
- **The Vault side stays offline.** The Vault core and the WebView keep no network code (cargo-deny bans, the CSP, `scripts/check-network-source.mjs`). The app gains no shell, HTTP or filesystem plugin and no general command execution: four argument-free commands (`companion_status`, `companion_start`, `companion_stop`, `companion_setup`), with supervision kept outside `AppCore`.
- **One grant at a time, off by default.** Nothing starts during ordinary use. The owner's explicit Start issues one grant ending at an absolute time at most one hour away; the broker enforces it before the credential read, before listening and before every admission, including direct loopback calls that skip the agent bridge. Each Start writes a fresh delegated agent token, removed on every stop. Owner Stop, any lock of the Vault (Auto-lock, Lock, focus loss when chosen), sleep, screen lock, user switch, grant expiry and app exit stop it. A crash, a helper that starts over, or a broker that stops unexpectedly is reported; nothing restarts by itself.
- **One pinned source.** `src-tauri/companion/companion.lock.json` pins the companion commit, its `policy.json` SHA-256 and the official Node.js release (v24.22.1) by SHA-256. `scripts/package-companion.sh` verifies all three, bundles only runtime files, and re-signs Node without upstream's `get-task-allow`, `allow-dyld-environment-variables`, `disable-library-validation` and executable-page exceptions (only `allow-jit` and sandbox inheritance remain). The helper refuses to start if the bundled policy differs from the pinned hash.
- **Windows:** unavailable until its boundary is built and verified.

## Consequences

- encrypted-note no longer makes an unconditional "never connects to the internet" promise for the whole app. The **Vault** never connects to the internet; when the owner starts the Agent Companion, text an approved agent supplies goes to OpenAI and can be billed, and the generated text returns to that agent and may enter its cloud conversation.
- **Custody limit, stated plainly:** the helper keeps the Agent Key in a plain-text owner-only (0600) file inside its own container and holds it in Node.js memory while running. That is not encrypted Vault storage, and JavaScript memory cannot be reliably erased. The Agent Key must therefore be new, narrowly scoped, short-lived and hard-capped at OpenAI, and revocable there; stopping the helper is not revocation.
- **Isolation limits:** the helper's sandbox separates it from the Vault's container and the Vault app's process. It does not protect the Agent Key from other software running as the owner with broader rights, from a compromised OS, or from an agent that has been given the owner's account; agents still run in a separate standard account (see the setup guide). An approved agent can still misuse every call the grant permits, up to the limits.
- **Readiness is reported in two parts.** Local readiness (runtime, plan, Agent Key file, handoff folder, standard agent account, protected code) is checked by the helper. The private ChatGPT connection is set up from the agent account and counts as working only after an observed end-to-end call; the app never reports it as connected.
- **Build inputs are fetched at packaging time** (git, npm, nodejs.org), verified against the pins. The resulting app makes no such fetches.

## Considered Options

- **A child process of the app:** rejected. It inherits the app's sandbox and could read the Vault's container (spike evidence above), and listening would require widening the Vault app's own entitlements.
- **Rewriting the broker inside the Vault's Rust process:** rejected. It would put network code and an Agent Key into the process that holds the Vault's keys.
- **Managing an externally installed companion only:** kept as the companion's standalone launcher, but not the integrated path: it depends on a separately installed Node and gives the owner two places to manage one grant.
