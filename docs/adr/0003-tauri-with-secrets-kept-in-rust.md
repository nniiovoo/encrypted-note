# Tauri v2, with secret custody in Rust and native adapters

The app must run on Mac and Windows and support **Capture Hiding** on both. We chose Tauri v2: the screens are TypeScript in the system WebView, and the Rust/native core owns key derivation, encryption, the **Vault** file and OS integration. The WebView is treated as untrusted. Native controls own actual **Master Password** and **Recovery Key** entry, **Recovery Kit** display/confirmation and stored **Wallet Kind** readouts. Ordinary Show receives one authorized **Hidden Field**, which is dropped when it hides. New/edited Hidden Field inputs still pass through the WebView. Rust wipes its own secret buffers; JavaScript strings and OS/native copies cannot be promised erased.

## Considered Options

- **Electron**: all TypeScript, but secrets would live in JS memory that can't be wiped (Bitwarden desktop issue #6231: master password found in memory dumps), plus the largest attack surface and an 8-week Chromium upgrade treadmill.
- **Flutter**: one codebase and a better mobile path later, but a new language, and Capture Hiding needs native code on each platform.
- **Native SwiftUI + a separate Windows app**: strongest per-platform integration (the research favoured SwiftUI for a Mac-only app) but two apps to build.

## Consequences

- Stay on Tauri v2 (2.11.6+, which includes the GHSA-w28w-mhc8-qvjv IPC fix), not the v3 alpha, and expect a v3 migration later. Use a single webview.
- Turn on Capture Hiding with `"contentProtected": true` in the window config, so it's active from creation and needs no JS permission. Use Tauri's isolation pattern and a strict CSP (`connect-src 'none'`), and grant only the capabilities needed.
- Keep npm and crate dependencies minimal and pinned (`npm ci --ignore-scripts`, `cargo-deny`/`cargo-vet`). npm (Sept 2025, and a malicious `@bitwarden/cli` in Apr 2026) and crates.io (2025, Aug 2026) have both shipped malware that stole wallet keys or secrets.
- Seed Phrase words are typed into one `<input type="password">` per word. WKWebView and Chromium turn on Secure Event Input for password fields, but not for a `<textarea>`. Secret inputs disable autocorrect, spellcheck, text replacement and Writing Tools.
- Mac **Quick Unlock** selects the local Swift CryptoKit Secure Enclave route, implemented in this source tree with physical acceptance pending. A current-biometric-set/private-key-use ACL gates real P-256 ECDH; HKDF-SHA256 and AES-GCM wrap a Rust-owned Vault Key plus authenticated credential-header binding in an encrypted private local file. No persistent Keychain item, Keychain access-group entitlement, Apple Developer account/profile or server is part of this route. Only the Vault Key is enrolled; Wallet actions still require a fresh native Master Password. No userPresence, device-password fallback, biometryAny, OR policy, community biometry plugin or software-key fallback is used. Unsupported hardware/constraints fail closed. Windows Hello remains later. See [Quick Unlock custody and acceptance](../quick-unlock-design.md).
- What "untrusted" does and does not cover. Rust freezes the requested action and source state before showing native controls, derives credentials outside the core mutex, and rechecks operation epoch, session generation, phase, exact file, target state, expiry and Sharing Guard before committing. Native callbacks never return credentials, a reusable authentication grant or stored Wallet plaintext through IPC. The browser can still request a native prompt, observe newly entered Hidden Fields (including new Wallet values), receive ordinary explicit Show values, or imitate a credential prompt. The owner must recognize the real native flow. Native custody closes the actual WebView Master Password/Recovery Key path; it does not make compromised renderer input/output trustworthy. [Issue #13's implementation](../native-credential-design.md) still needs physical keyboard/accessibility/capture acceptance.
- Wiping is best effort. Rust wipes owned keys and payloads, and the allocator wipes heap blocks as they are freed. The Swift crypto adapter clears its owned plaintext Data where supported. The stack, JavaScript strings, CryptoKit/LocalAuthentication internals, native editor/AppKit strings, OS clipboard and other OS copies are outside that guarantee. The Swift adapter is trusted native code in the same process; native custody is not protection against compromise of that process or the OS.
- Early spike: build a **sandboxed** Mac Tauri app (the container then asks before other apps read the Vault folder) without `network.client`; see the open risk in ADR-0001.

Quick Unlock's private file uses filesystem access controls, not application access-group isolation. Another process with the same user's file access can copy its encrypted Secure Enclave representation and request its own biometric-gated operation. This app's startup/seven-day Master Password gates constrain this app, not such another process. Removing the current file does not promise erasure of snapshots/backups or revocation of an older copied representation on the same Mac. The Vault header/body binding and process gates must still be checked after every protected release; no biometric boolean authorizes an open.

The disclosure budget is shared across Show, whole-field copying, line copying and `NAME=value` copying. A field is identified by Note id and field name; repeated use renews that same slot for 60 seconds, and visible metadata copies do not use a slot. Input validation and Wallet authorization happen before admission. Once admitted, a clipboard attempt uses its slot even if the OS refuses the write, matching Show-and-copy; failed calls do not return a value or start a reveal. Locking and unlocking does not reset the allowance.
